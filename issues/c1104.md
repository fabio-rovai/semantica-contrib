Follow-up evidence on how this one behaves in practice, because it turns out the mismatch is invisible to the validator the package ships with.

Running the generated shapes against an instance of the class they describe, with pySHACL 0.25 (the `shacl` extra):

```
shapes: sh:targetClass <https://semantica.dev/shapes/Person>, sh:path <https://semantica.dev/shapes/fullName>, sh:minCount 1
data:   <https://example.org/p1> a <https://semantica.dev/ns#Person> .   # no fullName

pySHACL          conforms = True
```

No violation, no warning, no indication that zero focus nodes were selected. A conforming report and a report where nothing was examined are the same bytes, so a pipeline that gates on `conforms` publishes unvalidated data with a green light.

I verified the same pair with a second, independent validator (the Rust engine in [open-ontologies](https://github.com/fabio-rovai/open-ontologies), which I maintain), which reports focus-node counts:

```
conforms:         null
focus_nodes:      0
unmatched_shapes: shapes/PersonShape → shapes/Person
                  shapes/OrganizationShape → shapes/Organization
warning:          no focus nodes matched: all 2 shape(s) target classes absent
                  from the data, so conformance is undetermined
```

Not posting this as a plug for another tool, but because it changes how severe this issue is. The namespace disagreement is not merely a wrong result that a user would notice and investigate. Through pySHACL it is unobservable, so the failure is silent by construction and no amount of care on the user's side surfaces it.

Worth considering whether the validation report should carry the number of focus nodes selected regardless of how the namespace question is resolved, since that single field turns this whole class of bug from silent into visible.
