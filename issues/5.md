### Summary

When an entity has no `id`, `serialize_to_turtle()` synthesises one from Python's builtin `hash()`:

```python
entity_id = f"semantica:entity_{hash(entity_text)}"
```

`hash()` on `str` is randomised per process by PYTHONHASHSEED, so the same knowledge graph exported twice produces different IRIs. The same pattern is used for `rel_base_id` in `_owl_time_triples_for_rel()`.

### Version

semantica 0.6.5, Python 3.13.

### Reproduction

Run this twice, as two separate processes:

```python
from semantica.export.methods import export_rdf
kg = {"entities": [{"text": "Acme Corp", "type": "https://example.org/Org"}], "relationships": []}
export_rdf(kg, "out.ttl", format="turtle")
print([l for l in open("out.ttl") if "entity_" in l])
```

### Actual

```
run 1: <semantica:entity_1966390833113473535> a <https://example.org/Org> ;
run 2: <semantica:entity_-1569031364158313747> a <https://example.org/Org> ;
```

### Why it matters

1. **Identity is not stable across runs.** Re-exporting the same graph yields a different graph. Diffing two exports, deduplicating against an earlier load, or resolving a provenance record written by an earlier run all break. This is hard to square with the project's provenance and audit-trail guarantees.
2. **The IRI is not what the prefix declares.** `<semantica:entity_...>` inside angle brackets is an absolute IRI with the scheme `semantica`, not `https://semantica.dev/ns#entity_...`. It parses, so nothing complains, but it never matches the declared prefix expansion used elsewhere in the same file, including the N-Triples serializer.

### Expected

A deterministic mint, for example `hashlib.sha256(text.encode()).hexdigest()[:16]`, written as a proper IRI in the declared namespace (`https://semantica.dev/ns#entity_<hash>`) or as the prefixed name `semantica:entity_<hash>` without angle brackets.

Point 2 applies to the default type as well: `entity.get("type", "semantica:Entity")` reaches `<semantica:Entity>`, so entities that fall back to the default type get a type IRI that no SHACL `sh:targetClass` or OWL class in the `https://semantica.dev/ns#` namespace will ever match. That is the same failure mode as #1082, reached from the data side rather than the shape side.
